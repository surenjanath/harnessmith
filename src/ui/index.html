How it works

    
The solver model attempts the goal with the project's base harness (system prompt, guardrails, memory, tool guidance, skills, sub-agents, scripts, hooks). The improver model reads those attempts and proposes harness edits along two dimensions: how the agent works (INV) and what a practitioner knows (DOM). Each edit is probed with a fresh attempt, and a composer merges what the evidence supports. The selector then picks the best final output without seeing which harness made it, and writes a lesson into the project library for the next goal. Budget per goal: 4k solver runs and 3k improver sessions.

Accuracy check · what the harness adds to a model

    
Asks a model questions that have one exact answer (arithmetic, percentages, dates, counting, statistics, and sums and lookups over CSV, JSON and log files). The questions are generated from a seed, so the right answers are computed, and no model has seen them. Each is asked to the model alone and through the harness.

Accuracy boost 

    
When a goal asks for one exact answer (a number, a name, a date), the solver writes a short program instead of answering from memory. The harness runs it, repeats the attempt independently and keeps the answer most attempts agree on; the agreement is reported as confidence. In every other goal the agent gets python and calc tools, and figures it writes are checked against what it actually read or computed.

What heals itself

    
    
      
  • Model failover: give a role a chain, e.g. local/qwen2.5-7b, openai/gpt-4.1-mini. A failing endpoint trips a circuit breaker after 3 errors and calls move to the next model; when the cooldown ends, the primary is tried again. If every model is down, the agent waits for the first to recover instead of failing.
    • 
      
  • Agent self-checks: the same call 3 times → "change approach", 5 times → blocked (3 for sub-agents), and a session that keeps repeating is ended; 4 failing calls in a row → "re-read the errors"; budget nearly gone with nothing written → "deliver now"; finish is refused while the deliverable fails review (missing file type, fake PDF, placeholders). Tool calls written as text, or with broken JSON, are repaired; a tool schema sent back as arguments is refused with an example.
    • 
      
  • Models over time: a model that has failed most of its recent calls moves behind the healthy ones in its chain; breaker state and measured speed are saved, so a restart remembers them. A key added to .env is picked up without a restart.
    • 
      
  • Rollouts and runs: a rollout that errors is retried once; a run that fails or ends partial because of a model or transport failure is retried, reusing everything already finished; runs interrupted by a restart resume automatically.
    •

How memory works

        

          
RECALL: the solver searches notes from earlier goals before planning

          
REMEMBER: it saves durable facts and techniques as candidates

          
SETTLE: after a run, notes from the adopted attempt and base runs become active; the rest are archived

          
PROMOTE: adopted notes are appended to the base harness's LongTermMEMORY.md

          
PIN: pinned notes go into every solver's instructions

          
MEANING: with an embedding model, recall matches by meaning, not only shared words

          
FADE: unused notes rank lower over time (30-day half-life) and are archived after 90 days; pinned ones never fade

          
SAFE: notes that look like keys or tokens are refused; memory lives outside the harness

        

        
        
        
        
        

      

    

  

  

    
Experience · verified answers kept as worked examples · 

      

    
When independent attempts agree on an answer, the question and the program that computed it are kept here. The next question of the same kind gets that program as a worked example. Sleep is what the project does with them while idle, after Google Research's “Language Models Need Sleep”: it consolidates (one example per kind of question; the ones that never helped are forgotten), then dreams: it turns each example into a new practice task by changing the data, computes the right answer by running the verified program on the changed data, and checks whether the model gets it right alone and with the example. It can also ask itself new questions about your files and keep the answers every attempt agrees on.
